## 1. Faits à vérifier

- [ ] **F1** · étape « Qui demande, qui répond », 🟢 : c'est toujours le client qui commence la conversation ; le serveur répond à chacun séparément. Source : aucune trouvée dans le dossier (définition implicite ; voir V1).
- [ ] **F2** · étape « Qui demande, qui répond », 🟡 : un serveur est d'abord un programme qui attend ; par extension, l'ordinateur qui le fait tourner ; n'importe quel ordinateur peut jouer ce rôle. Source : aucune trouvée dans le dossier.
- [ ] **F3** · étape « Qui demande, qui répond », 🔴 : un gros site répond avec des centaines de serveurs derrière une seule adresse grâce à des répartiteurs de charge ; un seul serveur peut héberger des milliers de petits sites. Source : aucune trouvée dans le dossier pour les répartiteurs ; pour l'hébergement de plusieurs sites, [RFC 9110, § 7.2, en-tête Host] https://www.rfc-editor.org/rfc/rfc9110.txt.
- [ ] **F4** · étape « Qui demande, qui répond », 🔴 : les réseaux « pair à pair » n'ont pas de serveur central, chaque machine est client et serveur. Source : aucune trouvée dans le dossier.

- [ ] **F11** · étape « Les ports », 🟢 : l'adresse IP désigne la machine, le port le programme ; site web sur 443, SSH sur 22. Source : registre des ports de l'IANA (dossier : 22 ssh, 443 https), https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml. Vérifié localement dans `/etc/services` : 22/tcp ssh, 443/tcp https.
- [ ] **F12** · étape « Les ports », 🟡 : l'IANA tient le registre : 80 HTTP, 443 HTTPS, 21 FTP, 22 SSH et SFTP, 25 courriel entre serveurs, 53 DNS. Vérifié dans `/etc/services` : 21 ftp, 22 ssh, 25 smtp, 53 domain, 80 http, 443 https. « SFTP sur 22 » n'est pas une entrée du registre (voir V3).
- [ ] **F13** · étape « Les ports », 🟡 : on peut faire tourner un site sur le port 8080, à condition de l'écrire dans l'URL. Source : aucune dans le dossier ; RFC 3986 (port explicite dans l'autorité). `/etc/services` : 8080/tcp http-alt.

## 2. Points de vigilance

- [ ] **V1** · étape « Qui demande, qui répond », 🟢 (« Une règle ne bouge jamais : c'est toujours le client qui commence la conversation ») : formulation absolue contredite dans le module même. En FTP **mode actif** (RFC 959, connexion de données du port 20, `PORT`), c'est le serveur qui ouvre la connexion de données vers le client ; c'est justement le protocole présenté à l'étape 5. Proposition : « C'est le client qui ouvre la conversation : c'est même ce qui le définit. » et, en 🔴 de l'étape 5, une phrase sur les modes actif et passif.
- [ ] **V2** · étape « Les ports », vérifie : « Sous Linux ou macOS, la commande `ss -tln` » est faux pour macOS : `ss` (paquet iproute2) n'existe que sous Linux. Proposition : « Sous Linux, `ss -tln` ; sous macOS, `netstat -an | grep LISTEN` (ou `lsof -iTCP -sTCP:LISTEN`) ; sous Windows, `netstat -an` ».
- [ ] **V3** · étape « Les ports », 🟡, bilan point 2 et animation `Ports` (ligne « 22 SSH, SFTP ») : la phrase « L'IANA tient le registre… 22 pour SSH et SFTP » laisse croire que SFTP est enregistré sur le port 22. Le registre (dossier) n'a que « 22 ssh » ; SFTP passe sur 22 parce qu'il est un sous-système de SSH. Le nom « sftp » est enregistré à l'IANA sur le port **115** pour un autre protocole (Simple File Transfer Protocol, RFC 913), à confirmer dans le registre (absent du `/etc/services` local). Proposition : « 22 pour SSH (et donc SFTP, qui voyage dans SSH) ».
- [ ] **V4** · étape « Les ports », 🔴 : « les ports dynamiques (49 152 à 65 535)… que ton ordinateur choisit au hasard pour son côté de chaque connexion ». Sous Linux, la plage par défaut est **32 768 à 60 999** (vérifié localement : `/proc/sys/net/ipv4/ip_local_port_range` = `32768 60999`) ; Windows suit la plage IANA. Proposition : « … que ton ordinateur choisit pour son côté de chaque connexion (Windows les prend dans cette plage ; Linux, par défaut, entre 32 768 et 60 999) » ; sourcer (RFC 6056 pour le tirage au hasard, documentation du noyau Linux).
- [ ] **V5** · étape « Qui demande, qui répond », histoire : « le premier protocole de transfert de fichiers de l'ARPANET » est un « premier·e X » sans nuance ni seconde source (règle de `CLAUDE.md` et des critères communs). Proposition : « l'une des premières descriptions d'un protocole de transfert de fichiers pour l'ARPANET » ou ajouter une source historique (niveau 2) qui l'établit. Même remarque pour « déjà l'idée du client et du serveur » : interprétation à appuyer sur une citation de la RFC 114.
- [ ] **V6** · étape « Qui demande, qui répond », histoire : « le premier serveur web tourne au CERN, sur l'ordinateur NeXT de Tim Berners-Lee » ne repose que sur le texte d'une **page d'erreur** de home.cern (dossier, § « Web au CERN ») ; aucune source dans `<Sources>` ne porte ce fait. Proposition : retrouver la page « The birth of the web » de home.cern (ou une archive) et une source indépendante (Computer History Museum, livre de Berners-Lee *Weaving the Web*), puis l'ajouter au dossier et à `<Sources>`.
- [ ] **V7** · histoire (étapes 0 et 3) et mythe (étape 2) : « le premier site, info.cern.ch, est toujours en ligne » et `https://info.cern.ch/` « le premier site web ». Ce qui est en ligne aujourd'hui est, à ma connaissance, une **restauration** faite par le CERN (projet de 2013) d'une copie de 1992, et l'adresse d'origine était en `http://` (HTTPS n'existait pas). Ni la restauration ni sa date ne sont dans le dossier. Proposition : « le premier site, info.cern.ch, a été remis en ligne par le CERN » et écrire `http://info.cern.ch/` dans le mythe, ou préciser « aujourd'hui servi en HTTPS » ; sourcer la restauration.
- [ ] **V8** · étape « FTP, FTPS, SFTP », 🟡 et histoire : la page cite côte à côte le port 990 et la RFC 4217 « qui normalise la version chiffrée ». La RFC 4217 ne normalise que le mode **explicite** (`AUTH TLS` sur le port 21) ; le mode implicite sur 990 vient seulement du registre IANA (dossier). Proposition : « soit dès la connexion (port 990, un usage courant mais non normalisé), soit, comme le prévoit la RFC 4217, en le demandant sur le port 21 avec `AUTH TLS` ». Vérifier ce point dans le texte de la RFC 4217.
- [ ] **V9** · étape « De l'URL au fichier », 🟡 : `index.html` pour un dossier et la redirection 301 sans barre finale sont des comportements d'Apache (module mod_dir : `DirectoryIndex`, `DirectorySlash`), non sourcés dans le dossier. Proposition : ajouter la documentation Apache de mod_dir au dossier et à `<Sources>`.
- [ ] **V10** · étape « FTP, FTPS, SFTP », histoire : « le dernier [brouillon] date de 2006 ». Le dossier ne vérifie que le draft-13. Deux nuances non sourcées : la version d'SFTP réellement déployée (OpenSSH) est la **version 3**, décrite par un brouillon plus ancien (draft-ietf-secsh-filexfer-02, 2001), pas le draft-13 cité ; et l'IETF a pu relancer des travaux sur SSH depuis (à vérifier sur datatracker.ietf.org avant validation). Proposition : vérifier sur le datatracker, puis écrire « le dernier brouillon du groupe de travail date de 2006 ; la version utilisée partout, la 3, vient d'un brouillon de 2001 », ou marquer l'encart « état au [date] ».
- [ ] **V11** · étape « Une conversation HTTP », 🔴 : « HTTP est décrit par la RFC 9110… La première ligne contient la méthode, le chemin et la version ». La ligne de requête et le format texte relèvent de la **RFC 9112** (HTTP/1.1), pas de la RFC 9110 ; HTTP/2 (RFC 9113) et HTTP/3 (RFC 9114) ne sont pas dans le dossier ; « plus rapide » n'est pas sourcé. Proposition : « La sémantique de HTTP est décrite par la RFC 9110 (2022), sa forme texte HTTP/1.1 par la RFC 9112 » ; ajouter les RFC 9112, 9113 et 9114 ; remplacer « plus rapide » par « plus compacte » ou le sourcer.
- [ ] **V12** · étape « FTP, FTPS, SFTP », 🔴, et animation `Transfert` : la vérification de l'empreinte de la clé d'hôte est décrite dans la RFC 4251 (architecture SSH), citée par le dossier (registre : « 22 ssh (RFC 4251) ») mais absente de `<Sources>`. Proposition : ajouter la RFC 4251.
- [ ] **V13** · animation `Transfert`, FTPS, étape 1 : « (poignée de main TLS : certificat du serveur visible) ». C'est vrai en TLS 1.2, faux en **TLS 1.3**, où le certificat est chiffré. En FTPS explicite, l'espion verrait aussi `AUTH TLS` et la réponse 234 en clair avant le chiffrement. Proposition : « (poignée de main TLS : en TLS 1.2, le certificat du serveur est visible) » ou « (poignée de main TLS) ».

## 3. Simplifications à valider

- [ ] **S1** · étape « Qui demande, qui répond », 🟢 et 🟡 : « le serveur, c'est un programme » ; « par extension, l'ordinateur ». Réalité : les deux sens coexistent dans l'usage professionnel (on achète « un serveur ») ; la page le dit bien. À valider.
- [ ] **S2** · étape « Les ports », 🟢 : analogie immeuble / appartement. Réalité : une machine peut avoir plusieurs adresses IP, et une adresse peut être partagée par plusieurs machines (NAT, répartiteurs). Acceptable en 🟢, le module Adresses IP nuance.
- [ ] **S3** · étape « Les ports », 🔴 : « une connexion est identifiée par quatre nombres ». Réalité : pour TCP, oui (RFC 9293) ; dans le système, on ajoute le protocole (TCP ou UDP), d'où le « quintuplet ». La page ne dit pas qu'il s'agit de TCP. Proposition éventuelle : « Une connexion TCP… ».
- [ ] **S4** · étape « Lire une URL », 🟢 : une URL dit trois choses (schéma, serveur, chemin). Réalité : RFC 3986 distingue aussi l'utilisateur, la requête et le fragment (traités en 🟡 et 🔴) ; « URL » vs « URI » non abordé. À valider.
- [ ] **S5** · étape « De l'URL au fichier », 🟢 : « un site n'est rien d'autre qu'un dossier ». Réalité : vrai pour un site statique (dit « sur un serveur web simple ») ; la configuration (réécritures, `.htaccess`) peut casser la correspondance ; le 🔴 nuance avec les programmes. À valider.
- [ ] **S6** · étape « FTP, FTPS, SFTP », 🟢 : « FTPS et SFTP, eux, chiffrent tout ». Réalité : en FTPS, le canal de données n'est chiffré que si le client le demande (`PBSZ` / `PROT P`, RFC 4217), et la commande `CCC` peut repasser les commandes en clair ; en FTPS explicite, le début de la connexion est en clair. En SFTP, l'échange de versions SSH est en clair (RFC 4253, dossier). Simplification acceptable en 🟢 si le 🔴 dit « bien configuré ».
- [ ] **S7** · étape « Un fichier, trois chemins », 🟢 et 🔴 : `public_html` « (ou `www`) ». Réalité : chez cPanel, `www` est habituellement un lien symbolique vers `public_html` (un seul dossier, deux noms) ; la page laisse croire à deux noms possibles. Proposition éventuelle : « `public_html` (aussi accessible sous le nom `www`) ».
- [ ] **S8** · étape « Un fichier, trois chemins », 🟡 et animation `Acces` : « Recharge le navigateur : la nouvelle version est déjà là. » Réalité : un cache (navigateur, serveur, CDN) peut servir l'ancienne version un moment ; pour rouages.net, le `.htaccess` demande de toujours revalider le HTML, mais pas pour les autres fichiers. Acceptable en 🟡.
- [ ] **S9** · étape « Un fichier, trois chemins », 🔴 : « un accès SSH ou SFTP voit tout ce que le compte a le droit de lire ». Réalité : chez beaucoup d'hébergeurs cPanel, le shell est enfermé (« jailshell ») ou le SFTP limité (chroot) ; la phrase reste juste au sens « ce que le compte a le droit de lire ».
- [ ] **S10** · étape « FTP, FTPS, SFTP », 🔴 : « une autre [connexion] pour chaque transfert de données ». Réalité : aussi pour chaque liste de dossier (`LIST`), et le mode bloc de la RFC 959 peut garder la connexion ; modes actif et passif non mentionnés (voir V1).
- [ ] **S11** · étape « Une conversation HTTP », 🟡 et animation `Requete` (échange « Deux sites, une seule adresse IP ») : la ligne `Host` suffit à choisir le site. Réalité : en HTTPS, le serveur doit choisir son certificat **avant** de lire `Host`, grâce à l'extension TLS SNI (RFC 6066) envoyée par le client ; c'est elle qui a rendu possible l'hébergement mutualisé en HTTPS. Proposition : une phrase en 🔴.
- [ ] **S12** · étape « Une conversation HTTP », 🟡 : familles de codes « comme des chiffres de dizaines » (en fait des centaines) ; 3xx présenté comme « c'est ailleurs », alors que 304 (Not Modified) n'est pas une redirection vers ailleurs ; famille 1xx omise. Proposition : « se lisent par leur premier chiffre ».
- [ ] **S13** · étape « Une conversation HTTP », vérifie : touche F12. Réalité : sur macOS, Cmd+Option+I ; Safari demande d'activer le menu Développement. Proposition éventuelle : « (F12, ou Cmd+Option+I sur Mac) ».
- [ ] **S14** · animation `Requete` : requêtes HTTP/1.1 montrées sans la ligne vide finale, sans `Content-Length`, et sans les en-têtes qu'un navigateur envoie (`User-Agent`, `Accept`…). Réalité : formes minimales valides côté requête (RFC 9112 exige `Host`, présent) ; acceptable comme illustration.
- [ ] **S15** · animation `Transfert`, FTP : l'espion ne voit que `220`, `USER`, `PASS`, `RETR` ; les réponses (331, 230, 150, 226) et la commande `PASV`/`PORT` sont omises. Acceptable ; les lignes affichées suivent la RFC 959 (dossier).
