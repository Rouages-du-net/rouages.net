## 1. Faits à vérifier

- [ ] **F1** · chapô, 🟢 : une adresse IP est un nombre de 32 bits en IPv4, de 128 bits en IPv6. Source : [8] RFC 791 https://www.rfc-editor.org/rfc/rfc791 ; [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291.
- [ ] **F2** · étape « IPv4, quatre octets », 🟢 : quatre nombres de 0 à 255, chacun sur un octet de 8 bits ; 4 × 8 = 32 bits (calcul vérifié). Source : [8] RFC 791 https://www.rfc-editor.org/rfc/rfc791.
- [ ] **F3** · étape « IPv4 », 🟡 : 2³² adresses, « environ 4,3 milliards » (4 294 967 296, calcul vérifié). Source : [8] RFC 791 (32 bits) https://www.rfc-editor.org/rfc/rfc791 ; le nombre est un calcul.
- [ ] **F4** · étape « IPv4 », 🟡 : c'est « moins que d'humains sur Terre, et bien moins que d'appareils connectés ». Source : aucune trouvée dans le dossier.
- [ ] **F5** · étape « IPv4 », 🟡 : adresses privées 10.x.x.x, 172.16 à 172.31.x.x, 192.168.x.x (calcul vérifié : 172.16.0.0/12 va de 172.16.0.0 à 172.31.255.255), utilisées seulement à l'intérieur d'un réseau local. Source : [11] RFC 1918 https://www.rfc-editor.org/rfc/rfc1918.
- [ ] **F6** · étape « IPv4 », 🟡 : trois plages, dont 192.0.2.x, sont réservées aux exemples. Source : [12] RFC 5737 https://www.rfc-editor.org/rfc/rfc5737.
- [ ] **F7** · étape « IPv4 », 🔴 : la RFC 1918 définit les plages privées ; une box les traduit en une adresse publique (NAT). Source : [11] RFC 1918 https://www.rfc-editor.org/rfc/rfc1918 pour les plages ; NAT : aucune trouvée dans le dossier (voir V4).
- [ ] **F8** · étape « IPv4 », 🔴 : plages de documentation 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24 (RFC 5737), qui ne désignent aucune vraie machine. Source : [12] RFC 5737 https://www.rfc-editor.org/rfc/rfc5737.
- [ ] **F9** · étape « IPv4 », histoire : IPv4 est décrit en septembre 1981 dans la RFC 791. Source : [8] RFC 791 https://www.rfc-editor.org/rfc/rfc791.
- [ ] **F10** · étape « IPv4 », histoire : le 3 février 2011, l'IANA, qui gère la réserve mondiale, distribue ses derniers blocs aux cinq registres régionaux. Source : [18] NRO, « Free Pool of IPv4 Address Space Depleted » https://www.nro.net/ipv4-free-pool-depleted/.
- [ ] **F11** · étape « IPv4 », histoire : le 25 novembre 2019, le RIPE NCC annonce avoir épuisé sa réserve. Source : [19] RIPE NCC, « The RIPE NCC has run out of IPv4 Addresses » https://www.ripe.net/publications/news/the-ripe-ncc-has-run-out-of-ipv4-addresses/.
- [ ] **F12** · étape « IPv4 », mythe : les réserves libres des registres sont épuisées, mais les adresses déjà distribuées servent toujours, se revendent ou se partagent (une box partage une adresse publique). Source : [18] et [19] pour l'épuisement ; la revente n'est mentionnée que dans les « Points d'attention » du dossier, sans source (voir V2).
- [ ] **F13** · étape « IPv6 », 🟢 : 128 bits, quatre fois plus qu'IPv4, écrits en 8 groupes de 4 chiffres hexadécimaux séparés par « : ». Source : [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291.
- [ ] **F14** · étape « IPv6 », 🟡 : deux règles de raccourci (zéros en tête effacés, une seule suite de groupes nuls remplacée par « :: ») ; `2001:0db8:0000:0000:0000:0000:0000:0001` devient `2001:db8::1` (vérifié avec `ipaddress`). Source : [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291 ; [17] RFC 5952 https://www.rfc-editor.org/rfc/rfc5952.
- [ ] **F15** · étape « IPv6 », 🟡 : 2¹²⁸ adresses, « environ 3,4 × 10³⁸ » (3,4028 × 10³⁸, calcul vérifié). Source : [15] RFC 4291 (128 bits) https://www.rfc-editor.org/rfc/rfc4291 ; le nombre est un calcul.
- [ ] **F16** · étape « IPv6 », 🔴 : selon la RFC 4291, la plupart des adresses ont un identifiant d'interface de 64 bits, donc un réseau local est en général un /64. Source : [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291.
- [ ] **F17** · étape « IPv6 », 🔴 : la RFC 5952 fixe une écriture unique : zéros en tête supprimés, « :: » le plus long possible (le premier en cas d'égalité), jamais pour un seul groupe, minuscules. Source : [17] RFC 5952 https://www.rfc-editor.org/rfc/rfc5952.
- [ ] **F18** · étape « IPv6 », 🔴 : 2001:db8::/32 est réservé à la documentation (RFC 3849). Source : [13] RFC 3849 https://www.rfc-editor.org/rfc/rfc3849.
- [ ] **F19** · étape « IPv6 », mythe : un seul « :: » par adresse, sinon on ne saurait pas combien de groupes chacun remplace. Source : [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291 (la règle est dans la RFC, mais le dossier ne la reprend pas explicitement).
- [ ] **F20** · étape « Le masque », 🟢 : un masque a trois écritures : /24, 255.255.255.0, 24 bits à 1 puis 8 bits à 0 (vérifié). Source : [9] RFC 950 https://www.rfc-editor.org/rfc/rfc950 ; [10] RFC 4632 https://www.rfc-editor.org/rfc/rfc4632.
- [ ] **F21** · étape « Le masque », 🟡 : les 1 sont toujours à gauche ; un octet de masque ne peut valoir que 0, 128, 192, 224, 240, 248, 252, 254 ou 255 (vérifié pour /0 à /32) ; /17 = 255.255.128.0 (vérifié). Source : [10] RFC 4632 https://www.rfc-editor.org/rfc/rfc4632 (contiguïté non citée explicitement dans le dossier ; voir V5).
- [ ] **F22** · étape « Le masque », 🟡 : l'adresse du réseau s'obtient par un ET logique entre l'adresse et le masque. Source : [9] RFC 950 https://www.rfc-editor.org/rfc/rfc950.
- [ ] **F23** · étape « Le masque », 🔴 : un /n compte 2³²⁻ⁿ adresses ; la première désigne le réseau, la dernière sert à la diffusion ; il reste 2³²⁻ⁿ − 2 machines. Source : « Points d'attention » du § 2 du dossier ; [9] RFC 950 https://www.rfc-editor.org/rfc/rfc950.
- [ ] **F24** · étape « Le masque », 🔴 : un /31 relie deux routeurs avec ses 2 adresses (RFC 3021), un /32 désigne une seule machine. Source : [14] RFC 3021 https://www.rfc-editor.org/rfc/rfc3021 ; /32 : « Points d'attention » du dossier.
- [ ] **F25** · étape « Le masque », histoire : en 1981, la RFC 791 découpait les adresses en classes A (réseau sur le premier octet), B (deux octets), C (trois octets). Source : [8] RFC 791 https://www.rfc-editor.org/rfc/rfc791.
- [ ] **F26** · étape « Le masque », histoire : les masques de sous-réseau arrivent en août 1985 (RFC 950). Source : [9] RFC 950 https://www.rfc-editor.org/rfc/rfc950.
- [ ] **F27** · étape « Le masque », histoire : en 1993, pour freiner l'épuisement des classes B, le CIDR permet toute longueur de préfixe, notée « /n » (RFC 1519, remplacée en 2006 par la RFC 4632). Source : [10] RFC 4632 https://www.rfc-editor.org/rfc/rfc4632 (la RFC 1519 n'a pas de source à elle dans le dossier, seulement sa date ; voir V6 et V8).
- [ ] **F28** · étape « Le masque », mythe : 255.0.255.0 n'est pas un masque, car ses 1 ne sont pas tous à gauche (binaire vérifié : 11111111.00000000.11111111.00000000). Source : [10] RFC 4632 https://www.rfc-editor.org/rfc/rfc4632 (implicite ; voir V5).
- [ ] **F29** · étape « Le masque », mythe : une adresse en 192.168 n'est pas forcément un /24, c'est la box qui choisit le masque. Source : aucune trouvée dans le dossier.
- [ ] **F30** · bilan : les cinq points reprennent les étapes ; plages d'exemple 192.0.2.0/24 et 2001:db8::/32. Source : [12] RFC 5737 https://www.rfc-editor.org/rfc/rfc5737 ; [13] RFC 3849 https://www.rfc-editor.org/rfc/rfc3849.

## 2. Points de vigilance

Calculs : aucune erreur trouvée. Ont été vérifiés avec `python3 -c 'import ipaddress …'` toutes les valeurs de la page et des replis (binaire de 192.0.2.17, 2³², 2¹²⁸, plages RFC 1918, valeurs d'octet de masque, /17, 198.51.100.77/24, abréviations IPv6), ainsi que `src/lib/ip.ts` compilé, comparé à `ipaddress` sur 3 000 couples adresse/préfixe IPv4 tirés au hasard (/0 à /32 : réseau, diffusion, masque, nombre de machines) et 3 000 adresses IPv6 (écriture courte RFC 5952) : 0 écart.

- [ ] **V1** · étape « IPv4 », 🟡, « moins que d'humains sur Terre, et bien moins que d'appareils connectés » : deux chiffres datés sans source ni « état au ». Proposition : sourcer la population mondiale (source primaire, par exemple les projections de l'ONU) et le nombre d'appareils, avec « état au [date] » ; ou dire seulement « moins d'une adresse par humain », ce qui demande quand même une source pour la population.
- [ ] **V2** · étape « IPv4 », mythe, « Les réserves libres des registres sont épuisées » : c'est au présent et pour les cinq registres, alors que le dossier ne source que l'IANA (2011) et le RIPE NCC (2019). L'état des quatre autres registres (AFRINIC notamment) n'est pas vérifié. La revente d'adresses (« se revendent ») n'a pas de source : elle n'apparaît que dans les « Points d'attention » du dossier. Proposition : écrire « état au [date] » et ajouter `evolutif` au `<MiseAJour>`, ou restreindre la phrase à ce qui est sourcé (« la réserve de l'IANA et celle du RIPE NCC sont vides ») ; ajouter au dossier une source primaire sur les transferts d'adresses (politique de transfert d'un registre).
- [ ] **V3** · glossaire `ipv6` (`src/data/glossaire.ts`) : « IPv4, dont les adresses sont épuisées » contredit le mythe de l'étape 0, pour qui ce sont les réserves libres qui sont épuisées. Proposition : « IPv4, dont les réserves d'adresses libres sont épuisées ». Ce glossaire sert à tout le site : vérifier que la nouvelle formulation convient aux autres modules.
- [ ] **V4** · étape « IPv4 », 🔴, « une box les traduit en une adresse publique (NAT) » : le NAT n'est ni dans ce dossier ni dans le bloc Sources de la page. Il est sourcé dans `docs/sources/entree-a-la-page.md` (RFC 3022, source [2-6], et RFC 6598 pour le NAT d'opérateur). Proposition : ajouter la RFC 3022 au bloc `<Sources>` (en reprenant l'URL de ce dossier), ou renvoyer explicitement au module « De l'Entrée à la page », qui le source déjà.
- [ ] **V5** · étape « Le masque », 🟡 « les 1 sont toujours à gauche […] jamais mélangés » et mythe « 255.0.255.0 n'est pas un masque » : la RFC 950 (1985), citée dans l'encart histoire, admettait à ma connaissance des bits de sous-réseau non contigus et recommandait seulement qu'ils le soient. Je n'ai pas pu le vérifier ici, mais le dossier indique que la RFC a été lue en entier. Les masques contigus sont une règle d'aujourd'hui (CIDR). Le dossier n'en dit rien. Proposition : vérifier le passage dans la RFC 950 ; si c'est confirmé, écrire « Aujourd'hui, dans un masque, les 1 sont toujours à gauche » et ajouter au dossier la citation de la RFC 950 et celle de la RFC 4632 sur la contiguïté.
- [ ] **V6** · étape « Le masque », histoire, « pour freiner l'épuisement des classes B » : le dossier ajoute « et, à terme, de l'espace IPv4 ». Les RFC du CIDR invoquent aussi, il me semble, la croissance des tables de routage. Je ne l'ai pas vérifié, et le dossier ne le mentionne pas. Proposition : relire l'introduction de la RFC 4632 et, si c'est confirmé, écrire « pour freiner l'épuisement des classes B et la croissance des tables de routage ».
- [ ] **V7** · bloc `<Sources>`, auteurs : la RFC 791 (1981) est attribuée à l'« IETF », alors que l'IETF n'a été créée qu'en 1986. La RFC 791 a été rédigée sous la direction de J. Postel (à vérifier sur son en-tête). Les RFC 1918, 5737, 3849 et 8200 sont aussi signées « IETF » au lieu des noms de leurs auteur·es. Pour la RFC 1918, `entree-a-la-page.md` donne « Y. Rekhter et al. ». Proposition : reprendre les noms qui figurent dans l'en-tête de chaque RFC, comme pour les RFC 950, 4632, 3021, 4291 et 5952.
- [ ] **V8** · bloc `<Sources>` : la RFC 1519 est citée dans le texte (date de 1993) mais ne figure ni dans le bloc Sources ni dans la liste des sources du dossier. La RFC 8200 est listée dans le bloc mais n'est citée nulle part dans le texte. Proposition : ajouter la RFC 1519 au dossier puis au bloc après l'avoir ouverte, ou retirer son numéro du texte (« le CIDR, en 1993, aujourd'hui décrit par la RFC 4632 ») ; garder la RFC 8200 seulement si elle sert.
- [ ] **V9** · liens d'archive : `docs/SOURCES.md` (« Liens morts ») demande de garder un lien d'archive dans le code source pour chaque source web. Ni la page ni `bases-ip.md` n'en ont, contrairement à `entree-a-la-page.md`. Proposition : ajouter des liens Internet Archive, au moins pour les deux actualités NRO [18] et RIPE NCC [19], qui risquent plus de disparaître que les RFC.
- [ ] **V10** · `<MiseAJour date="2026-11-05" />` et `verifie="2026-11-05"` : le texte a été retravaillé après cette date (le ton a été appliqué à ce module le 27 novembre 2026, selon `docs/CHARTE.md`, « Ton des textes »). Proposition : à la validation, mettre les deux dates à jour ensemble.
- [ ] **V11** · étape « IPv6 », 🟡, « Ainsi <code>2001:0db8:…</code> fond en » : « Ainsi » fait partie des tournures que la charte demande d'éviter. Proposition : « Par exemple, `2001:0db8:…` fond en `2001:db8::1`. »
- [ ] **V12** · animation `Ipv4.astro` (ligne 89) et `nature()` dans `src/lib/ip.ts` : toute adresse qui n'est ni privée (RFC 1918) ni de documentation (RFC 5737) est annoncée comme « une adresse publique possible ». C'est faux pour 127.0.0.1 (bouclage), 169.254.x.x, 100.64.0.0/10 (NAT d'opérateur, RFC 6598), 0.x.x.x, 224.0.0.0 et au-delà (multidiffusion, réservé), et 255.255.255.255. Proposition : écrire « Cette adresse n'est ni privée ni réservée aux exemples », ou traiter les plages spéciales dans `nature()` en sourçant le registre IANA des adresses à usage spécial (RFC 6890), qu'il faudrait ajouter au dossier.

## 3. Simplifications à valider

- [ ] **S1** · chapô, 🟢, et glossaire `adresse-ip` (« Numéro qui identifie une machine ») : en réalité, une adresse IP désigne une interface réseau. Une même machine peut en avoir plusieurs (IPv4 et IPv6, Wi-Fi et câble).
- [ ] **S2** · étape « IPv4 », 🟡, « ne servent qu'à l'intérieur d'un réseau local, derrière une box » : les plages privées servent aussi dans les entreprises et les centres de données. Chez les opérateurs, le NAT à grande échelle utilise une autre plage, 100.64.0.0/10 (RFC 6598).
- [ ] **S3** · étape « IPv4 », 🟡, « trois plages […] réservées aux exemples » : c'est exact pour la documentation en IPv4. D'autres plages spéciales (bouclage 127.0.0.0/8, lien local, multidiffusion) ne sont pas mentionnées, ce qui se défend à ce niveau.
- [ ] **S4** · étape « IPv4 », histoire, « le registre européen (RIPE NCC) » : il couvre l'Europe, le Moyen-Orient et l'Asie centrale (dossier, [19]).
- [ ] **S5** · étape « IPv4 », histoire, l'IANA « distribue ses derniers blocs aux cinq registres régionaux » : il s'agit, à ma connaissance, des cinq derniers blocs /8, un par registre. À confirmer dans [18] si l'on veut préciser.
- [ ] **S6** · étape « IPv6 », 🟢, « 8 groupes de 4 chiffres » : c'est la forme complète. Une fois abrégé, un groupe s'écrit avec 1 à 4 chiffres et vaut toujours 16 bits.
- [ ] **S7** · étape « IPv6 », 🟡, « de quoi ne plus jamais en manquer » : formule forte. Comme on distribue les adresses par /64 et par /48, l'espace se consomme bien plus vite que 2¹²⁸ adresses une à une. À garder comme effet, ou à nuancer (« de quoi voir venir »).
- [ ] **S8** · étape « Le masque », 🔴, « un /31 relie deux routeurs » : la RFC 3021 vise les liaisons point à point en général, et les routeurs en sont le cas courant.
- [ ] **S9** · étape « Le masque », histoire, classes A, B, C « réseau sur le premier octet / deux / trois » : la classe se lit sur les premiers bits (0, 10, 110). Les classes D et E viennent plus tard. Simplification acceptable.
- [ ] **S10** · étape « Le masque », histoire, « Les masques de sous-réseau arrivent en août 1985 » : la RFC 950 est le standard, mais des propositions l'ont précédée (RFC 917, 1984, à vérifier ; absente du dossier). Selon la ligne éditoriale (« démonter les “premier·e X” »), « sont normalisés » serait plus juste qu'« arrivent ».
- [ ] **S11** · étape « Le masque », mythe, « c'est la box qui choisit le masque » : c'est la configuration de la box (son serveur DHCP), que l'on peut changer. À un autre endroit, c'est l'administrateur·rice du réseau qui le fixe.
- [ ] **S12** · animation `Ipv6.astro`, étape 1, « Les 4 premiers groupes (64 bits) désignent le plus souvent le réseau » : fidèle à la RFC 4291 (« la plupart »). L'animation n'accepte pas la notation avec une IPv4 incluse (`::ffff:192.0.2.1`), pourtant valide (RFC 4291) : elle la déclare invalide.

## 4. Animations

- [ ] **A1** · `Ipv4` : quatre champs d'octet, 32 bits cliquables (boutons avec `aria-pressed` et une étiquette « Octet n, bit de poids … »), puis l'adresse en 32 bits, en hexadécimal et en un seul nombre. Repli sans JavaScript vérifié : 192 = 11000000, 0 = 00000000, 2 = 00000010, 17 = 00010001. Valeurs affichées par défaut, vérifiées : hexadécimal `c0 00 02 11`, nombre 3 221 226 001. Exemples proposés : 198.51.100.200 (documentation), 192.168.1.10 et 10.0.0.1 (privées). À regarder : le message « adresse publique possible » (V12), et le fait qu'une saisie hors de 0 à 255 est ramenée dans cet intervalle sans message.
- [ ] **A2** · `Ipv6` : pas à pas en 4 étapes (forme complète, zéros en tête, plus longue suite nulle, « :: »). Le repli est juste (`2001:0db8:…:0001` → `2001:db8:0:0:0:0:0:1` → `2001:db8::1`). Résultats des exemples, vérifiés avec `ipaddress` : « deux suites de zéros » → `2001:db8:0:1::ff` ; « égalité » → `2001:db8::1:0:0:1` ; « un seul groupe nul » → `2001:db8:0:1:1:1:1:1` ; « déjà abrégée » → `2001:db8::a:b`. Les groupes colorés sont masqués aux lecteurs d'écran (`aria-hidden`), mais la légende (`aria-live`) décrit chaque étape. À regarder : le message d'erreur pour une saisie invalide, et la notation avec une IPv4 incluse, refusée (S12).
- [ ] **A3** · `Masque` : curseur /0 à /32, boutons /8, /16, /17, /24, /26, /30, /31, champ de masque, table des bits (adresse, masque, ET = réseau) et liste des résultats. Repli vérifié : 198.51.100.77/24 → réseau 198.51.100.0, diffusion 198.51.100.255, 254 machines ; /17 = 255.255.128.0. Cas limites, vérifiés dans le code : /31 affiche « aucune » diffusion et 2 machines, /32 une seule adresse, /0 4 294 967 296 adresses. Le mythe dit « Essaie-le dans l'animation » : taper 255.0.255.0 dans « Masque » n'affiche le refus qu'à la validation (Entrée ou sortie du champ), et le préfixe précédent reste affiché. Couleurs « vert / jaune » de la note : `--ill-secret-b` et `--ill-commun`, cohérentes avec le texte. La table est `aria-hidden` : vérifier que la légende et la liste suffisent avec un lecteur d'écran, et l'affichage à 375 px (la grille passe sur une colonne sous 30rem).
