## 1. Faits à vérifier

- [ ] **F1** · chapô, 🟢 : une école, une entreprise, « même ta box » reçoivent un bloc d'adresses et le découpent (salles, administration, Wi-Fi des invité·es). Source : aucune trouvée dans le dossier (voir V5).
- [ ] **F2** · étape « Couper en parts égales », 🟢 : emprunter 1, 2 ou 3 bits donne 2, 4 ou 8 parts ; /24 devient /26 ; chaque part a la moitié, le quart, le huitième des adresses (vérifié). Source : [20] RFC 950 https://www.rfc-editor.org/rfc/rfc950 ; [21] RFC 1878 https://www.rfc-editor.org/rfc/rfc1878.
- [ ] **F3** · étape « Parts égales », 🟡 : k bits empruntés donnent 2ᵏ sous-réseaux de 2³²⁻ⁿ adresses chacun, moins l'adresse du sous-réseau et celle de diffusion ; pour des /26 : 192.0.2.0, .64, .128, .192 (vérifié avec `ipaddress … subnets(new_prefix=26)`). Source : [21] RFC 1878 https://www.rfc-editor.org/rfc/rfc1878 ; « Points d'attention » du § 2 du dossier.
- [ ] **F4** · étape « Parts égales », 🔴 : un /n commence toujours à un multiple de 2³²⁻ⁿ ; 192.0.2.32/26 n'existe pas et désigne en fait 192.0.2.0/26 (vérifié : `ipaddress` refuse 192.0.2.32/26 en mode strict, « host bits set », et donne 192.0.2.0/26 sinon). Source : aucune explicite dans le dossier ([10] RFC 4632 https://www.rfc-editor.org/rfc/rfc4632 serait la référence ; voir V9).
- [ ] **F5** · étape « Parts égales », 🔴 : la RFC 1878 donne la table de tous ces découpages. Source : [21] RFC 1878 https://www.rfc-editor.org/rfc/rfc1878.
- [ ] **F6** · étape « Parts égales », histoire : les sous-réseaux sont décrits en août 1985 (RFC 950), et cette règle excluait le premier et le dernier sous-réseau (« tout à 0 », « tout à 1 »). Source : [20] RFC 950 https://www.rfc-editor.org/rfc/rfc950 (citation : « should not be assigned to actual (physical) subnets » ; voir V3).
- [ ] **F7** · étape « Parts égales », histoire : en 1995, la RFC 1878 déclare cette pratique obsolète ; on utilise tous les sous-réseaux. Source : [21] RFC 1878 https://www.rfc-editor.org/rfc/rfc1878 (« This practice is obsolete! ») ; [22] RFC 1812 https://www.rfc-editor.org/rfc/rfc1812.
- [ ] **F8** · étape « Parts égales », mythe : « Depuis 1995, on les utilise tous : 4 sous-réseaux /26, pas 2 » (calcul vérifié). Source : [21] RFC 1878 https://www.rfc-editor.org/rfc/rfc1878.
- [ ] **F9** · étape « Des parts à la bonne taille », 🟢 : besoins de 100, 50 et 20 appareils ; le VLSM, ce sont des masques de longueurs différentes dans un même réseau. Source : [21] RFC 1878 (*Variable Length Subnet Table*) https://www.rfc-editor.org/rfc/rfc1878 ; le dossier ne donne pas de définition explicite du VLSM.
- [ ] **F10** · étape « Bonne taille », 🟡 : la méthode consiste à trier les besoins du plus grand au plus petit, à prendre le plus petit bloc tel que 2ᵏ − 2 ≥ nombre de machines, et à le poser au premier endroit libre bien aligné. Source : aucune (c'est une méthode) ; vérifiée par le calcul (voir V1).
- [ ] **F11** · étape « Bonne taille », 🔴 : une liaison entre deux routeurs recevait un /30 (4 adresses, dont 2 utilisables) ; depuis la RFC 3021 (2000), un /31 suffit, sans adresse de réseau ni de diffusion. Source : [14] RFC 3021 https://www.rfc-editor.org/rfc/rfc3021.
- [ ] **F12** · étape « Bonne taille », 🔴 : le VLSM s'appuie sur le routage sans classes (CIDR, RFC 4632). Source : [10] RFC 4632 https://www.rfc-editor.org/rfc/rfc4632 pour le CIDR ; le lien entre VLSM et CIDR n'est pas dans le dossier (voir V10).
- [ ] **F13** · étape « Bonne taille », mythe : un plan laisse de la marge, sinon il faut tout renuméroter quand on ajoute des appareils. Source : aucune trouvée dans le dossier (bonne pratique).
- [ ] **F14** · étape « Exercices corrigés », 🟢 : six types d'exercices tirés au hasard, avec une correction pas à pas. Source : le code (`src/lib/exercices-ip.ts`, `TYPES`) ; vérifié.
- [ ] **F15** · étape « Exercices », 🟡 : un numéro donne toujours le même exercice ; les adresses sont 192.0.2.x, 198.51.100.x, 203.0.113.x ou 10.x.x.x. Source : [12] RFC 5737 https://www.rfc-editor.org/rfc/rfc5737 ; [11] RFC 1918 https://www.rfc-editor.org/rfc/rfc1918 ; vérifié sur 5 000 numéros, aucune adresse hors de ces plages (voir V2 pour le numéro).
- [ ] **F16** · étape « Exercices », 🔴 : la taille de bloc vaut 256 moins l'octet du masque qui n'est ni 255 ni 0 ; pour /27 (255.255.255.224), 256 − 224 = 32, et les réseaux commencent à 0, 32, 64, 96… (vérifié). Source : « Points d'attention » du § 3 du dossier (méthode de calcul ; voir V8).
- [ ] **F17** · étape « Et en IPv6 ? », 🟢 : chaque réseau local reçoit un /64, qui contient bien plus d'adresses qu'il n'y aura jamais d'appareils (2⁶⁴). Source : [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291 ; [24] RFC 7421 https://www.rfc-editor.org/rfc/rfc7421.
- [ ] **F18** · étape « IPv6 », 🟡 : un fournisseur attribue par exemple un /48 ou un /56, ce qui laisse 16 ou 8 bits jusqu'au /64, soit 65 536 ou 256 réseaux locaux (vérifié). Source : [23] RFC 6177 https://www.rfc-editor.org/rfc/rfc6177 (le /48 de l'ancienne RFC 3177 et les /56 encouragés par les registres sont mentionnés dans le dossier).
- [ ] **F19** · étape « IPv6 », 🟡 : un chiffre hexadécimal vaut 4 bits, donc le numéro du réseau local se lit dans le 4ᵉ groupe. Source : calcul ; [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291 (voir S7).
- [ ] **F20** · étape « IPv6 », 🔴 : la limite /64 vient de l'identifiant d'interface de 64 bits (RFC 4291), et la RFC 7421 (2015) explique pourquoi garder cette frontière fixe. Source : [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291 ; [24] RFC 7421 https://www.rfc-editor.org/rfc/rfc7421 (voir V11).
- [ ] **F21** · étape « IPv6 », 🔴 : la RFC 6177 (2011) ne fixe pas de taille pour les sites, mais demande qu'ils obtiennent « au moins un /64, et dans la plupart des cas bien plus », pour ne jamais avoir à économiser les adresses. Source : [23] RFC 6177 https://www.rfc-editor.org/rfc/rfc6177 (citation présente dans le dossier ; la fin de la phrase n'y figure pas, voir V12).
- [ ] **F22** · étape « IPv6 », mythe : en pratique, on donne un /64 par réseau local, quelle que soit sa taille. Source : [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291 ; [24] RFC 7421 https://www.rfc-editor.org/rfc/rfc7421 (voir S6).
- [ ] **F23** · bilan : k bits donnent 2ᵏ sous-réseaux ; sous-réseaux alignés ; VLSM du plus grand au plus petit ; tous les sous-réseaux s'utilisent depuis 1995 ; un /31 pour deux routeurs ; un /64 par réseau local, numéroté dans le 4ᵉ groupe. Source : [21] RFC 1878 https://www.rfc-editor.org/rfc/rfc1878 ; [14] RFC 3021 https://www.rfc-editor.org/rfc/rfc3021 ; [15] RFC 4291 https://www.rfc-editor.org/rfc/rfc4291.

## 2. Points de vigilance

Calculs : aucune erreur dans les valeurs affichées. Ont été vérifiés avec `python3 -c 'import ipaddress …'` : les découpages /24 → /26, l'exemple 192.0.2.32/26, l'exemple /27, les replis de `Decoupe`, `PlanVLSM` et `Ipv6Sites`, ainsi que 2¹⁶, 2⁸ et 2⁶⁴. J'ai aussi compilé `src/lib/ip.ts` : 500 plans VLSM tirés au hasard, sans chevauchement, chaque bloc aligné et le plus petit possible. J'ai compilé `src/lib/exercices-ip.ts` : 5 000 exercices tirés au hasard et les 6 exercices du repli, toutes les réponses et toutes les lignes binaires des corrections sont justes. Les points ci-dessous portent sur la formulation et sur des cas limites.

- [ ] **V1** · étape « Bonne taille », 🟡, « trier les besoins du plus grand au plus petit », et `planVLSM()` dans `src/lib/ip.ts` (ligne 149) : le tri se fait sur le nombre de machines, pas sur la taille du bloc. Avec une liaison en /31 (2 machines) suivie d'un réseau de 1 ou 2 machines sans la case « Liaison » (donc un /30), le plan laisse un trou. Vérifié : en ajoutant un réseau de 1 machine au plan par défaut, on obtient 192.0.2.224/31 puis 192.0.2.228/30 ; 192.0.2.226 et 192.0.2.227 restent inutilisées, et le message final « Il reste … adresses libres en fin de bloc » ne compte pas ce trou. Proposition : trier par taille de bloc (préfixe le plus court d'abord) dans `planVLSM()` et dans `tries()` de `PlanVLSM.astro`, et écrire « trier les blocs du plus grand au plus petit » ; ajouter un test. → Corrigé le 28/11/2026 : `trierBesoins()` (tri par préfixe) partagé par `planVLSM()` et l'animation, texte « du plus grand bloc au plus petit », test ajouté. Reste à valider.
- [ ] **V2** · étape « Exercices », 🟡, « le même numéro donne toujours le même exercice » : ce n'est vrai qu'avec le même « Type » choisi dans la liste. Vérifié : le n° 42 en « tous les types » donne « Écrire le masque /22 », alors qu'avec un type imposé il porte sur 198.51.100.217/25. Si deux élèves n'ont pas choisi le même type, « Faites tous l'exercice n° 42 » ne fonctionne pas. Proposition : écrire « le même numéro, avec le même type, donne le même exercice », ou, dans `exercice()`, tirer le type même quand il est imposé (cela changerait les numéros actuels). Le numéro change aussi si le code du tirage change : le signaler aux enseignant·es ?
- [ ] **V3** · étape « Parts égales », histoire (« Cette première règle interdisait ») et mythe (« sont interdits », « C'était la règle de 1985 ») : la RFC 950, citée dans le dossier [20], dit « should not be assigned ». C'est une recommandation, pas une interdiction. Proposition : « Cette première règle déconseillait d'utiliser… » ; mythe : « Le premier et le dernier sous-réseau sont à éviter. » C'était la recommandation de 1985.
- [ ] **V4** · étape « Parts égales », histoire, et bloc `<Sources>` : la page fonde « on les utilise tous » sur la seule RFC 1878. Il faut vérifier le statut actuel de cette RFC sur sa page rfc-editor : je crois qu'elle a été reclassée « Historic », sans pouvoir le confirmer ici. La RFC 1812 (juin 1995) [22], que la RFC 1878 cite comme « current, standards-based practice », figure dans le bloc Sources mais n'est jamais citée dans le texte. Proposition : « En 1995, la RFC 1812 sur les routeurs, puis la RFC 1878, font de l'usage de tous les sous-réseaux la pratique normale » (à ajuster après lecture), et noter le statut de la RFC 1878 dans le dossier.
- [ ] **V5** · chapô, 🟢, « même ta box reçoivent un bloc d'adresses… et le découpent » : en IPv4, une box reçoit en général une seule adresse publique, voire une adresse partagée en NAT d'opérateur. Elle numérote elle-même son réseau privé. C'est en IPv6 qu'elle reçoit un préfixe. Le dossier ne dit rien de la box. Proposition : « Une école, une entreprise reçoivent un bloc d'adresses… et le découpent », éventuellement suivi de « (en IPv6, même ta box reçoit un bloc) ».
- [ ] **V6** · étape « Bonne taille », 🟡 (« le plus petit bloc qui suffit ») et mythe (« Un plan laisse de la marge ») : les deux encarts se contredisent, et l'animation applique la règle sans marge (Administration : 20 machines dans un /27, 10 adresses libres, c'est le hasard). Bilan, point 3 : « chacun le plus petit bloc qui lui suffit ». Proposition : « le plus petit bloc qui suffit, en comptant les appareils à venir », dans le 🟡 et dans le bilan.
- [ ] **V7** · lettre k : à l'étape 0 (🟡) et au bilan, k désigne les bits empruntés (2ᵏ sous-réseaux) ; à l'étape 1 (🟡), dans l'animation `PlanVLSM` et dans les corrections des exercices (« 2^k − 2 ≥ … »), k désigne les bits de machine. Proposition : garder k pour les bits empruntés et prendre une autre lettre (h, ou « bits de machine » en toutes lettres) pour la formule 2ʰ − 2 ≥ N.
- [ ] **V8** · étape « Exercices », 🔴, astuce « 256 moins l'octet du masque qui n'est ni 255 ni 0 » : elle ne s'applique pas quand la frontière tombe entre deux octets (/8, /16, /24, où aucun octet n'est ni 255 ni 0). La taille obtenue se compte dans l'octet concerné : pour /20, 256 − 240 = 16 dans le 3ᵉ octet, soit 16 × 256 = 4 096 adresses. Le dossier le signale (§ 3, « Points d'attention »). Proposition : « … l'octet du masque où passe la frontière ; les réseaux avancent de cette valeur dans cet octet. S'il n'y en a pas, la frontière tombe pile entre deux octets. »
- [ ] **V9** · étape « Parts égales », 🔴, « 192.0.2.32/26 n'existe pas […] on désigne en fait 192.0.2.0/26 » : c'est vrai pour un nom de sous-réseau. Mais l'écriture adresse/préfixe sert couramment à désigner une machine dans son réseau, et c'est justement ce que font les exercices du même module (« l'adresse du réseau de 10.195.202.14/18 »). Proposition : « 192.0.2.32/26 n'est pas un sous-réseau : c'est la machine 192.0.2.32, dans le sous-réseau 192.0.2.0/26. » Citer la RFC 4632 pour l'alignement, en ajoutant le passage au dossier.
- [ ] **V10** · étape « Bonne taille », 🔴, « Le VLSM s'appuie sur le routage sans classes (CIDR, RFC 4632) » : ce lien n'est pas dans le dossier. Historiquement, les masques de longueur variable dans un même réseau précèdent le CIDR de 1993 (la RFC 1009, de 1987, en parlait, à vérifier) et dépendent de protocoles de routage qui transportent le masque. Proposition : sourcer, ou écrire « Le VLSM et le CIDR reposent sur la même idée : un préfixe de n'importe quelle longueur (RFC 4632). »
- [ ] **V11** · étape « IPv6 », 🔴, « la RFC 7421 (2015) explique pourquoi garder cette frontière fixe » : le dossier dit seulement « analyse de la frontière fixe ». La RFC 7421 est une analyse des avantages et des coûts. Proposition : vérifier sa conclusion dans le résumé ; à défaut, écrire « la RFC 7421 (2015) analyse ce que coûterait de déplacer cette frontière ».
- [ ] **V12** · étape « IPv6 », 🔴, « pour ne jamais avoir à économiser les adresses » : cette paraphrase n'est pas dans le dossier, qui ne cite que « at least one /64, and in most cases significantly more ». Par ailleurs, « demande » est fort pour une BCP qui recommande. Proposition : vérifier dans la RFC 6177 et citer le passage, ou supprimer la fin de la phrase ; « recommande » plutôt que « demande ».
- [ ] **V13** · animation `Ipv6Sites` : elle propose un /60, qui n'apparaît ni dans le texte de la page (« un /48 ou un /56 ») ni dans le dossier. Proposition : retirer le /60, ou le sourcer et le citer dans le texte (« /48, /56, parfois /60 »).
- [ ] **V14** · animation `Ipv6Sites`, repli (« de 2001:db8:abcd:0::/64 ») et légende (ligne 204, réseau n° 0) : l'écriture RFC 5952, enseignée dans le module précédent, est `2001:db8:abcd::/64` (vérifié avec `ipaddress`). Proposition : corriger le repli (« de 2001:db8:abcd::/64, le réseau n° 0, à 2001:db8:abcd:ffff::/64 ») et produire la légende avec `ecrireCourt()`.
- [ ] **V15** · animation `Exercices`, repli sans JavaScript (`Exercices.astro`, ligne 15) : le type est suivi d'un point, ce qui donne « Même réseau ?. ». Proposition : séparer le type de l'énoncé par « : » ou par un saut de ligne.
- [ ] **V16** · `src/lib/exercices-ip.ts`, cas déroutants : sur 5 000 numéros, 13 exercices « Même réseau ? » comparent une adresse avec elle-même, et 31 prennent comme seconde adresse celle du réseau ou de diffusion. Par ailleurs, 113 exercices « Adresse du réseau » ou « Adresse de diffusion » partent d'une adresse qui est déjà celle du réseau ou de diffusion. Les réponses restent justes. Proposition : exclure ces cas lors du tirage (cela changerait les numéros, à faire avant que des enseignant·es ne s'en servent), ou les accepter.
- [ ] **V17** · `<MiseAJour date="2026-11-06" />` et `verifie="2026-11-06"` : le texte a été retravaillé le 27 novembre 2026 (`docs/CHARTE.md`, « Ton des textes »). Proposition : à la validation, mettre les deux dates à jour ensemble.
- [ ] **V18** · bloc `<Sources>` : les RFC 5737, 1918 et 3849 sont attribuées à l'« IETF » au lieu de leurs auteur·es (pour la RFC 1918, `entree-a-la-page.md` donne « Y. Rekhter et al. »). Aucune source n'a de lien d'archive (`docs/SOURCES.md`, « Liens morts »). Proposition : reprendre les noms qui figurent dans l'en-tête de chaque RFC ; les liens d'archive sont moins urgents ici, car toutes les sources sont des RFC.
- [ ] **V19** · glossaire : la page n'utilise que `<Terme id="masque-reseau">`, dont la définition est juste. L'entrée `cidr` existe mais n'est pas reliée, alors que le texte parle de CIDR (étape 1). « Diffusion », « VLSM » et « liaison point à point » n'ont pas d'entrée. Proposition : relier « CIDR » à `<Terme id="cidr">` ; ajouter « VLSM » et « adresse de diffusion » au glossaire si on le juge utile.

## 3. Simplifications à valider

- [ ] **S1** · étape « Parts égales », 🟢, « Comme une pizza » : l'image ne vaut que pour des parts égales, et c'est bien le cas de cette étape.
- [ ] **S2** · étape « Parts égales », 🟡, « moins deux qu'on ne donne jamais à une machine » : la phrase dit « jamais », alors qu'il y a des exceptions, le /31 (RFC 3021) et le /32, que l'étape 1 mentionne pour le /31.
- [ ] **S3** · étape « Parts égales », histoire, « les logiciels modernes utilisent tous les sous-réseaux » : la formule reste générale, et certains vieux équipements ou réglages pouvaient encore exclure le sous-réseau zéro.
- [ ] **S4** · étape « Bonne taille », 🔴, « On lui donnait un /30 » : l'imparfait laisse croire que la pratique a disparu, alors que le /30 reste courant ; le /31 est une option.
- [ ] **S5** · étape « Bonne taille », 🟡, « premier endroit libre bien aligné » : avec des blocs triés par taille, cette méthode ne laisse jamais de trou (chaque bloc suivant est plus petit et tombe aligné). C'est juste, à condition de trier par taille de bloc (voir V1).
- [ ] **S6** · étape « IPv6 », 🟢 et mythe, « chaque réseau local reçoit un /64 […] quelle que soit sa taille » : les liaisons entre routeurs utilisent souvent un /127 (RFC 6164, absente du dossier). La phrase reste vraie pour les réseaux locaux.
- [ ] **S7** · étape « IPv6 », 🟡, « le numéro du réseau local se lit directement dans le 4ᵉ groupe » : c'est le groupe entier pour un /48 ; pour un /56, seulement ses 2 derniers chiffres, et pour un /60 le dernier. L'animation le montre en couleur.
- [ ] **S8** · animation `Ipv6Sites`, note « identifiant d'interface (64 bits, choisi par chaque machine) » : c'est vrai en autoconfiguration (SLAAC), mais l'identifiant peut aussi être attribué par DHCPv6 ou à la main.
- [ ] **S9** · exercices : IPv4 seulement, préfixes de /16 à /30 ; « Nombre de machines » ne propose jamais de /31 ni de /32. Le périmètre est cohérent avec le texte.

## 4. Animations

- [ ] **A1** · `Decoupe` : réseau de départ (de /1 à /29) et nouveau préfixe (curseur de p + 1 à min(30, p + 10)) ; bits colorés (réseau, empruntés, machines), barre d'au plus 64 blocs, liste des 16 premiers sous-réseaux puis « … et N autres ». Repli vérifié : 192.0.2.0/24 → 4 × /26, 64 adresses dont 62 machines, .0, .64, .128, .192. À regarder : les lettres « n » et « m », affichées à la place des bits empruntés et des bits de machine, ne sont pas expliquées dans la note ; une base non alignée (par exemple 192.0.2.77/24) est ramenée sans message à 192.0.2.0, ce qui serait une bonne occasion de montrer l'alignement (F4) ; les bits et la barre sont `aria-hidden`, mais la liste et la légende `aria-live` portent l'information ; vérifier la grille de 32 bits à 375 px.
- [ ] **A2** · `PlanVLSM` : tableau de besoins modifiable (nom, machines, case « Liaison »), pas à pas (tri, une attribution par étape, bilan). Repli vérifié : Wi-Fi 192.0.2.0/25 (126), salle 192.0.2.128/26 (62), administration 192.0.2.192/27 (30), liaison 192.0.2.224/31 (2), reste 192.0.2.226 à 192.0.2.255 (30 adresses). Sans la case « Liaison », la liaison prend 192.0.2.224/30 et il reste 28 adresses. À regarder : le texte 🔴 dit « Coche « Liaison » pour comparer » alors que la case est déjà cochée par défaut (il faudrait dire « Décoche ») ; les trous du V1 ; le message quand un besoin ne rentre plus (essayer 200 + 100 machines dans un /24) ; tous les boutons « Retirer ce réseau » ont la même étiquette, qui pourrait inclure le nom du réseau.
- [ ] **A3** · `Exercices` : sélecteur de type, numéro (le premier est tiré au hasard à chaque visite), vérification, score, correction dépliable. Les six exercices du repli (numéros 101 à 106), vérifiés : réseau de 10.195.202.14/18 → 10.195.192.0 ; diffusion de 198.51.100.193/26 → 198.51.100.255 ; machines d'un /20 → 4094 ; masque /30 → 255.255.255.252 ; préfixe pour 1 886 machines → /21 ; 10.167.161.34 et 10.167.185.123 en /19 → oui (même réseau, 10.167.160.0). La comparaison des réponses ignore les espaces, la casse et le « / » initial. À regarder : V2, V15 et V16 ; le verdict est annoncé (`aria-live`).
- [ ] **A4** · `Ipv6Sites` : choix /48, /56 ou /60 (préfixes vérifiés, bien alignés : 2001:db8:abcd::/48, 2001:db8:abcd:ab00::/56, 2001:db8:abcd:abc0::/60), curseur du numéro de réseau (de 0 à 65 535, 255 ou 15), adresse colorée (`aria-hidden`), légende complète. Repli vérifié (2¹⁶ = 65 536, 2⁸ = 256), sauf l'écriture du réseau n° 0 (V14). À regarder : le /60 (V13) ; dans le HTML, la sortie vaut « 0 » alors que le curseur vaut 1, une incohérence corrigée au chargement par le script mais visible si le script ne s'exécute pas (la scène reste alors masquée, donc sans conséquence).
