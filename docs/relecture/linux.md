## 2. Points de vigilance

- [ ] **V1** · étape « Les droits et leurs écritures », encart histoire : la phrase « Les droits sur les fichiers ont été brevetés » contredit la source. Le résumé du brevet dit « Access permission bits are used in the **prior art** » : les bits de permission existaient déjà, et le brevet porte sur une amélioration, que le dossier rattache au bit setuid (titre du § B9). Le dossier lui-même demande « À vérifier » (revendications non lues, pas de deuxième source). Proposition : lire les revendications, puis écrire par exemple « Dennis Ritchie dépose pour les Bell Labs un brevet sur une amélioration du contrôle d'accès aux fichiers (le bit setuid) » ; sinon, rester au plus près du résumé.
- [ ] **V2** · étape « Chemins absolus et relatifs », 🟡 (`cd ../bob` « te voilà dans /home/bob ») et animation `Terminal` (bouton `cd ../bob`, repli sans JavaScript) : sur un Ubuntu récent, les dossiers personnels sont créés en 750 (vérifié dans un shell : `HOME_MODE 0750` dans `/etc/login.defs`, `DIR_MODE=0750` dans `/etc/adduser.conf`). alice, qui n'est pas dans le groupe `bob`, recevrait « Permission non accordée ». De même, le terminal simulé laisse alice entrer dans `/root`, qui est en 700. Proposition : garder l'exemple en précisant « si bob a ouvert son dossier », ou prendre un exemple sans problème de droits (`cd ../../etc`, `cd /srv`) ; faire répondre « Permission non accordée » au terminal pour `/root` et `/home/bob`, ce qui annonce l'étape 4. La valeur 0750 d'Ubuntu n'est pas dans le dossier : à sourcer si on la cite.
- [ ] **V3** · étape « root et sudo », mythe (« `rm -rf / tmp` … n'a alors aucun garde-fou ») et animation `Terminal` (réponse à `rm` : « avec -rf et /, il tente d'effacer tout le système ») : GNU `rm` refuse `/` par défaut (`--preserve-root (default)`, vérifié avec `rm --help`, coreutils 9.4). Avec `rm -rf / tmp`, `/` serait refusé et `tmp` (relatif au dossier courant) effacé. L'exemple ne montre donc plus le danger. Proposition : prendre une faute qui passe vraiment, par exemple `rm -rf /etc /cours` ou `rm -rf ~ /cours` au lieu de `rm -rf ~/cours` (efface tout le dossier personnel), et retirer « tente d'effacer tout le système » ou ajouter « sauf garde-fou de `rm`, qui refuse `/` ». Ajouter rm(1) dans les sources.
- [ ] **V4** · animation `Droits` / `src/lib/linux.ts` (`appliquerChmod`) : le calcul de `=` **sans classe** est faux. `chmod =r` sur un fichier en 777 donne 466 (`r--rw-rw-`) dans la simulation, et 444 avec le vrai chmod (vérifié dans un shell). Le code ne remet à zéro que les bits hors du masque, alors que le vrai chmod efface tout le trio puis n'ajoute que les bits non masqués. Les autres cas testés sont justes (`+w`, `+x`, `g+w`, `g-w,o-rwx`, `u=rw,go=r`, `a+x`, `=rw`). Proposition : pour `=` sans classe, utiliser `touche = 7 << decalage` (sans masque), et ajouter un test unitaire `appliquerChmod(0o777, '=r') === 0o444`. → Corrigé le 28/11/2026, tests ajoutés (`=r`, `=rw`, `=w` comparés au vrai chmod). Reste à valider.
- [ ] **V5** · étape « Comptes et groupes », 🟡 (« `/etc/shadow`, que seul root peut lire »), `src/data/linux.ts` (`ARBRE` : « Lisible seulement par root » ; `CHAMPS_PASSWD`) : sous Debian et Ubuntu, le fichier est `-rw-r----- root shadow` (vérifié dans un shell). Les membres du groupe `shadow` peuvent donc le lire aussi. L'animation `Sudo` et `FICHIERS_DROITS` le montrent d'ailleurs (« Elle n'est ni root ni dans le groupe shadow »). Proposition : « que seuls root (et le groupe shadow, sous Debian et Ubuntu) peuvent lire » au niveau 🟡, ou garder « seul root » en 🟢 et nuancer en 🔴.
- [ ] **V6** · chapô (« Les 500 plus puissants supercalculateurs du monde tournent tous sous Linux ») et glossaire `linux` (même phrase) : c'est un chiffre qui change à chaque liste TOP500 (deux fois par an). La page n'a pas `evolutif` et n'écrit pas « état au ». Proposition : « Sur la liste TOP500 de novembre 2026, les 500 supercalculateurs… » (ou « depuis novembre 2017 »), dans la page comme dans le glossaire ; ou ajouter `evolutif`.
- [ ] **V7** · étape « root et sudo », « Vérifie » (`sudo grep sudo /var/log/auth.log` « sous Debian ou Ubuntu »), `ARBRE` (`/var/log/auth.log` « (Debian, Ubuntu) ») et animation `Sudo` (ligne « # /var/log/auth.log : … » dans un scénario Debian trixie, avec `apt update` sur `deb.debian.org … trixie`) : à ma connaissance, Debian n'installe plus rsyslog par défaut depuis Debian 12, et il n'y a alors pas de `/var/log/auth.log` (le journal est dans journald). Rien dans le dossier sur ce point (le conteneur n'a pas non plus de `auth.log`). Proposition : vérifier dans les notes de version de Debian 12, puis écrire « sous Ubuntu, `/var/log/auth.log` ; ailleurs, `journalctl _COMM=sudo` » et, dans l'animation, prendre soit Ubuntu partout, soit journald.
- [ ] **V8** · animation `Ssh`, étape 4 (« Tout est désormais chiffré. Le serveur prouve son identité avec sa clé d'hôte ») : dans SSH, la clé d'hôte et sa signature font partie de l'échange de clés lui-même (le serveur signe le résultat de l'échange, RFC 4253 §8) ; c'est ce qui empêche un intermédiaire de s'interposer. Le chiffrement ne démarre qu'après. La question « Are you sure…? » arrive donc avant le canal chiffré, pas après. L'ordre présenté (étape 3 en clair, étape 4 chiffrée + clé d'hôte) suggère une preuve d'identité après coup. Proposition : fusionner « échange de clés + signature par la clé d'hôte » en une étape, puis « canal chiffré » ; RFC 4253 est dans `<Sources>`, mais le § 8 n'est pas cité dans le dossier.
- [ ] **V9** · affirmations sans source dans le dossier, à sourcer ou à garder comme connaissance courante (décision du relecteur ou de la relectrice) : `www-data` comme compte du serveur web (étape 2 🟢 ; c'est le nom sous Debian et Ubuntu, pas sous Fedora) ; macOS et `/Users` (étape 0 🟡) ; `/proc` fabriqué par le noyau (étape 0 🔴) ; `visudo` (étape 5 🔴) ; le propriétaire peut faire `chmod`, seul root peut faire `chown` (étape 4 🟡, vérifiés dans un shell) ; même UID = même compte, `ls -l` qui affiche un nombre (étape 2, mythe) ; WSL « donne un vrai Linux » (étape 0, « Vérifie » : vrai pour WSL 2, pas pour WSL 1) ; `/var/www` par défaut pour Apache et `/dev/sda` « le premier disque » (`ARBRE` ; sur NVMe c'est `/dev/nvme0n1`). Proposition : ajouter au dossier les pages de manuel correspondantes (chown(2), visudo(8), proc(5)…) et corriger « vrai Linux » en « WSL 2 fait tourner un vrai noyau Linux ».
- [ ] **V10** · étape « Se connecter avec SSH », 🔴 (« SFTP et `scp` passent par la même connexion ») : ils utilisent le même **protocole**, mais chaque commande ouvre sa propre connexion SSH (sauf multiplexage `ControlMaster`). Proposition : « SFTP et `scp` passent eux aussi par SSH ».
- [ ] **V11** · étape « Se connecter avec SSH », 🔴 (« refuse une clé si `~/.ssh` ou `authorized_keys` peut être modifié par d'autres (droits 700 et 600) ») : la parenthèse donne les droits **recommandés** par ssh(1) comme si c'était la condition. sshd accepte aussi 755 et 644 (non modifiables par d'autres). sshd(8) vérifie aussi le **dossier personnel**, ce que le dossier note et que la page omet. Proposition : « … si `~/.ssh`, `authorized_keys` ou le dossier personnel peuvent être modifiés par d'autres (on recommande 700 et 600) ».
- [ ] **V12** · étape « root et sudo », 🔴 (« Ubuntu verrouille par défaut le mot de passe de root : on ne peut administrer qu'avec sudo ») : la doc Ubuntu citée dit le contraire de la seconde moitié : « This does not mean that the root account has been deleted, or that it may not be accessed ». Proposition : « … : par défaut, on administre avec sudo ». Ajouter aussi Fedora (root verrouillé depuis Fedora 28 si aucun mot de passe n'est donné, [D13], https://docs.fedoraproject.org/en-US/quick-docs/root-account-locked/) si l'on veut éviter un cas unique.
- [ ] **V13** · étape « Tout part de la racine », histoire (« Linus Torvalds, étudiant… annonce un système **libre** ») et glossaire `linux` (« Noyau … libre, lancé en 1991 ») : le message dit « (free) », sans préciser gratuit ou libre. À ma connaissance, les premières versions de Linux avaient une licence maison qui interdisait la vente, et le passage à la GPL date de 1992 ; rien dans le dossier sur ce point. Le statut d'étudiant n'est pas non plus dans la source citée (« Organization: University of Helsinki »). Proposition : « annonce un système gratuit (« free »), « juste un passe-temps » » ; vérifier et sourcer la date de passage à la GPL avant d'écrire « libre » pour 1991 ; sourcer « étudiant » ou écrire « à l'université d'Helsinki ».
- [ ] **V14** · étape « Se connecter avec SSH », histoire (« le Suédois Björn Grönvall ») : la citation de openssh.com/history.html reprise dans le dossier [E15] ne donne pas sa nationalité. Seul le § F21 l'affirme, en disant « déjà sourcé plus haut », ce qui n'est pas le cas. Proposition : vérifier sur la page (ou ailleurs) ; sinon, retirer « le Suédois ».
- [ ] **V15** · étape « Tout part de la racine », 🔴 (« Debian, Ubuntu et Fedora ont regroupé… ») : pour Ubuntu, le dossier n'a qu'une observation locale (**[non trouvé]**). Debian et Fedora sont sourcés, mais aucune de ces sources ne figure dans `<Sources>`. Proposition : ajouter à `<Sources>` les notes de version de Debian 12 et la page Fedora UsrMove ; pour Ubuntu, trouver une source ou écrire « Debian et Fedora (et, en pratique, Ubuntu) ».
- [ ] **V16** · bloc `<Sources>` : plusieurs sources lues du dossier qui portent des faits publiés en sont absentes : POSIX XBD chap. 4 (§ 4.7 et 4.16) et XCU chap. 2 (tilde) ; manuel coreutils « Numeric Modes » et « Mode Structure » ; pam_umask(8) (valeur 002) ; shadow(5), group(5), id(1), inode(7) ; RFC 4253 (port 22) ; sshd(8) ; wiki Debian sudo et sudoers de Fedora ; Debian 12 et Fedora UsrMove (V15). ## 3. Simplifications à valider

- [ ] **S1** · étape 0, 🟡 (« Branche une clé USB… il apparaît… sous `/media` ») : c'est l'environnement de bureau qui monte automatiquement la clé (souvent dans `/media/<compte>/<nom>`) ; sur un serveur sans bureau, il faut la monter à la main (`mount`, souvent dans `/mnt`). Le « par exemple » couvre-t-il assez ?
- [ ] **S2** · étape 0, 🟢 (« Sous Linux, absolument tout est rangé dans cet arbre-là ») : vrai pour les fichiers, les disques et les périphériques ; les interfaces réseau, par exemple, n'ont pas de fichier dans `/dev`. Acceptable au niveau 🟢 ?
- [ ] **S3** · étape 1, 🟢 (chemin absolu qui « marche d'où que tu sois ») : vrai, sauf cas rares (chroot, conteneurs). Simplification honnête.
- [ ] **S4** · étape 2, 🟢 (« Le serveur web… tourne sous le compte `www-data` ») : en général, le processus principal démarre en root puis ses processus de travail passent sous `www-data` ; le nom vaut pour Debian et Ubuntu. Le « en principe » qui suit suffit-il ?
- [ ] **S5** · étape 2, 🟡 (« il ne contient plus aucun mot de passe ») : c'est le cas quand le système utilise `/etc/shadow` (le champ vaut `x`), donc sur presque toutes les distributions ; passwd(5) dit « These days many people run… ». Acceptable.
- [ ] **S6** · étapes 3 et 4, 🟢 : le modèle propriétaire / groupe / autres omet les ACL, les capacités, SELinux et AppArmor, les attributs comme `chattr +i` et les montages en lecture seule. Faut-il une phrase 🔴 « il existe d'autres mécanismes (ACL…) » ?
- [ ] **S7** · étape 4, 🔴 (« un dossier en 700 protège tout ce qu'il contient ») : sauf contre root, contre un fichier aussi accessible par un lien physique placé ailleurs, et contre un programme qui l'a déjà ouvert. Simplification acceptable au niveau 🔴 ?
- [ ] **S8** · étape 5, 🟡 (sudo demande ton mot de passe, « Puis il consulte `/etc/sudoers` ») et glossaire `sudo` (« après avoir demandé le mot de passe… Chaque utilisation est journalisée ») : en réalité, sudo évalue d'abord la règle de sudoers, qui peut dispenser du mot de passe (`NOPASSWD`, délai de 5 minutes) ; pour une personne non autorisée, il demande quand même le mot de passe avant de refuser. La journalisation est le défaut, mais elle se règle. L'ordre présenté est celui que voit l'utilisateur·rice : à valider.
- [ ] **S9** · étape 6, 🟢 (« tout passe chiffré ») : les présentations (version du logiciel, liste d'algorithmes) passent en clair ; l'animation le montre. Acceptable.
- [ ] **S10** · étape 6, 🟡 (« la clé privée, elle, ne quitte jamais ton ordinateur ») : c'est la règle d'usage, pas une garantie technique. L'étape 7 montre justement le cas où on la copie sur le bastion. Tourner en « ne doit jamais quitter » ?
- [ ] **S11** · étape 7, 🟡 (rebond à la main : « le bastion voit tout passer en clair, et il faut lui confier sa clé ») : on peut aussi prêter l'agent (`-A`) sans copier la clé ; l'animation le précise, pas le texte. Ajouter « (ou lui prêter son agent) » ?
- [ ] **S12** · étape 7, 🟢 (« Les serveurs les plus importants ne sont pas joignables directement depuis internet ») : c'est la pratique recommandée, pas une règle universelle. Ajouter « en principe » ou « dans les réseaux bien tenus » ?
- [ ] **S13** · animation `Terminal` : `ls` ajoute un « / » aux dossiers (le vrai `ls` le fait seulement avec `-F` ou `-p`) et `ls -a` affiche `./ ../` au lieu de `. ..`. La légende dit que les vrais terminaux utilisent la couleur. Acceptable ?
- [ ] **S14** · animation `QuiPeut` : la sortie `id eve → uid=1002(eve) groupes=eve,eleves` est abrégée (le vrai `id` affiche `uid=1002(eve) gid=1002(eve) groupes=1002(eve),…`) ; la simulation compare les noms, pas les UID, alors que la page insiste sur « le noyau ne connaît que des numéros ». Acceptable pour une animation ?
- [ ] **S15** · animation `Ssh`, étape 3 (« une clé secrète par un échange de type Diffie-Hellman ») : les versions récentes d'OpenSSH utilisent par défaut un échange hybride (courbe X25519 + algorithme post-quantique) ; « de type Diffie-Hellman » reste juste pour la partie X25519.
